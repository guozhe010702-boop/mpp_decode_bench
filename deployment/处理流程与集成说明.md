# 处理流程与集成方案

```text
IMX415 → RKCIF RAW → RKAIQ/ISP → /dev/video44 NV12 3840×2160@60
 → DQBUF与单调时钟打点 → 最新原始帧槽(1张等待)
 → DMA-BUF直接导入 → MPP异步H.265编码(最多2张在途)
 → 组装完整access unit并严格按序 → MPP全4K硬解
 → 最新解码候选槽(1张) → 显示截止时间选择最新候选
 → DRM导入DMA-BUF → VOP缩放 → HDMI真实翻页事件
Python硬件采样 → Cairo/Pango透明ARGB → 独立HUD线程 → ARGB显示平面
```

1. 采集使用MMAP/EXPBUF，校验连续NV12的stride、offset和有效字节。8个已分配缓冲不表示积压8帧；原始等待槽最多1张，旧候选可被新帧替换。
2. 共享DMA-BUF省去每帧约12.44MB的CPU图像拷贝。Raw对象一直持有到编码最后输出片段完成并释放才QBUF，不能提交后立即归还相机缓冲。
3. MPP初始化前配置非阻塞输入；CBR20Mbps、GOP60、普通IP无B帧、关闭重编码。编码片段组装完整AU再解码，没有实现端到端slice子帧流水。
4. 帧ID通过MPP PTS传递，实际时间独立用CLOCK_MONOTONIC记录。压缩参考帧严格保序，不随机丢弃；严重错误当前退出清理，并未实现自动IDR重同步。
5. 解码有限等待20ms，帧就绪即返回，不是每帧固定睡20ms；特定MPP超时返回值兼容分支只在库SHA匹配时启用。
6. 显示由上次真实flip时间预测下一刷新，提前3.5ms取最新候选，最多1次未完成翻页。NONBLOCK不是撕裂式ASYNC；错过截止仍会多等一个刷新周期。
7. 当前扫描帧保留至下一翻页完成或关闭平面，避免MPP缓冲过早复用。NV12由VOP缩放，原生路径不使用GPU/RGA进行逐帧视频处理。
8. HUD独立ARGB双缓冲，状态free/writing/ready/pending。显示线程只取已准备好的HUD，不在翻页关键路径读文件。中文、FPS、温度、CPU/GPU/NPU/内存由Python采样，未知值显示--。
9. cpu_capacity动态选择大核；只对校验身份的3个RKAIQ RAW交接线程临时设RR/5，不全局修改IRQ/调频，停止恢复原策略。
10. 逐帧记录DQBUF、编码提交/完成、解码提交/完成、显示提交/flip；独立计数计算FPS和延迟P50/P95/P99/max。直方图0.1ms、CSV微秒；60fps吞吐不代表低延迟。

退出顺序：停止采集/编码提交，处理在途帧，等待线程，停HUD并关闭显示平面，释放扫描帧和MPP引用，销毁编解码器/相机，监督器恢复格式、线程策略和桌面。受控退出与ExecStopPost提供恢复，断电无法保证用户态清理执行。

## 集成到现有相机程序

优先独立进程方式：产品程序以参数数组调用control.py start/status/stop，读取active.json指向的status.json，保留当前监督和恢复逻辑。控制入口需要root权限；不要直接拼接不可信shell字符串。

相机和DRM都必须有唯一所有者。如果原产品已经采集同一V4L2节点，不能同时再启动本程序争抢采集；如果Qt/Wayland拥有显示，也不能同时独占KMS。先决定采集和显示由谁负责。

同进程集成时，需将main.cpp内Camera/Raw、Codec、Latest、Display/Picture、Trace拆成模块。外部采集接口至少提供fd、NV12布局、尺寸/stride/offset、ID、时间戳和归还回调；码流出口提供完整AU、参数头、PTS及关键帧标志；解码出口保留MPP帧引用和DMA-BUF布局，不能只保存fd而立即释放帧。这些API尚未封装，本包不是稳定SDK。

RTSP/网络推流、AI推理、录像不在当前原生链路内；增加后必须重新测量延迟、吞吐和热负载。历史FFmpeg脚本供对照，默认不启动mediamtx。

剩余瓶颈是取帧前RAW→ISP约32/49ms档位差异。应补齐内核完成事件与ISP调度测量再改BSP，本包未盲目启用early-buffer/wrap/自动readback。光学端到端、4K HDMI和物理热插拔需在目标系统另验。
